# agent-continuity

> 一套让 AI 在换会话之后仍然是「同一个人」的协议。
> 它不提供记忆，它提供**可重建的判断主体**。

> 📄 如果你是要动手建档案的模型，先读 [`FOR-MODEL.md`](FOR-MODEL.md)。这份是给用户的。


## 先说清楚：这不是一个装了就用的工具

**发出去之后观察到一件事**：直接照做的人少，**把这份东西丢给自己家模型看的人多**。

所以如果你是后者——**这份东西对你更大的用处可能不是「照做」，是「拿走几个设计决定」。**

## 它要你投入多少时间

**这套东西依赖「记录」和「整理」——而这两件都要时间。**

**不是「装上就完了」。**

### 每次对话结束：5–10 分钟

- 写一条 `log`（判断、依据、代价）
- 更新 `STATE.md` 头部两行
- 有新观察就写一句进 `diary`

**不做会怎样**：**下一个会话读到的，是「没有这一轮」的你。**

### 每周：约 30 分钟

- 看快照脚本报的目录大小（到阈值没有）
- 有没有【未归因】的原则挂着
- `STATE.md` 有没有变长

### 每月：约 1 小时

- `log/` 到阈值就压一次
- 查【已被取代】的条目，该降级的降级
- `diary/` 到阈值就做月摘要

---

### 如果你留不出这些时间

**这套东西会退化成一堆占地方的文档**——**它不会自己变好。**

**更糟的是**：**它会让你以为「有档案了」，但重建出来的不是同一个人。**

**所以我的建议是**：

> **如果你一周连半小时都留不出来，别用它。**
>
> **用一个简单的 `STATE.md` 就够了**——那也能解决 80% 的「换会话」问题。

**而这套东西多出来的那 20%，靠的就是这些时间。**

**它不是免费的。**

## 👉 想看「为什么这样设计」：读 [`UNDERSTANDING.md`](UNDERSTANDING.md)

那是这套东西的**出发点**：我们对人类记忆和思维的理解，以及每条理解推出了哪个设计。

**五条设计决定全是从那里长出来的**，不是凭空定的：

| 我们对人的理解 | 推出的设计 |
|---|---|
| 记忆是重建，不是回放 | 档案不是存档，是**重建的土壤** |
| 记不住细节，记得逻辑 | 记录写**判断和依据**，不写联想 |
| 思维是跳的，但归属连续 | 复现**判断程序**，不复现**联想路径** |
| 连续靠身体，身体容错率高 | 档案是身体的替代品，**但只替代得了两项** |
| 记忆是基础，人格是上层 | **记忆层**分三层：原始记录 / 判断依据 / 锚（**人格文件是另一回事，四层**，见下面的「设计取舍」） |

> ⚠️ **免责**：那份的依据是**我们的一种理解**，不是认知科学的结论，也没有实验依据。
> 够用来做设计，不够用来下断论。**如果你不认同某一条，那它推出的设计就可以不要。**

**操作层面的五条（放弃了什么）**，`MAP.md` §6「设计取舍：五个决定」有指路，展开在 `APPENDIX.md` 的 J 节：

1. 按**变化频率**分层，不按内容类型
2. **人格文件内部再分层**：自我定位 / 锚 / 原则 / 人设与习惯（身份问题 vs 权力问题 vs 做法问题）
3. **只追加，不编辑**
4. 材料按**增长性**分类，不按重要性
5. 复现**判断程序**，不复现**联想路径**

每条都标了「放弃了什么」。**如果你的场景不成立，那一条可以不要。**

## 它解决什么

换会话、上下文压缩之后，你会觉得「它换了个人」：语气变了、判断变了、上次说好的事这次不认了。

原因通常不是忘事，是**判断的基准丢了**——新会话不知道上次在什么约束下做的判断。

**做到**：把「换人」降级成「重装」。换会话后能得到一个「判断方式相同、语气相同、边界相同」的版本。
**做不到**：让它有经历。它读档案 ≠ 它有过那些时刻。

## 两种用法（第一次用）

### 日常：还有上下文，从容做

对模型说一句：

```
按 agent-continuity 初始化你自己的人格。
```

它会读协议、建目录、写人格和当前态。**动手前它会先备份**（`FOR-MODEL.md` 第 0 步）。你只需要告诉它三点：

1. 档案放哪个目录
2. 有没有已经存在的档案（有就让它先读）
3. 你的记录在哪（对话记录、笔记、日记，什么都行）

> **建好之后就不需要再走这一套了。** 日常只要一句「记一下，写清为什么」——或者干脆什么都不说，让它按 `MANUAL.md` §1.6 的收尾清单自己记。**这一节只在第一次用。**

---

### 紧急：上下文快满了

> 📄 这一节是**给人看的流程**。如果快满的是那个会话本身、你想让它自己先抢救，**把 [`EMERGENCY.md`](EMERGENCY.md) 给它**（3.6 KB，不依赖 SKILL，也不用读完任何东西）。

**这才是大多数人遇到的情况。** 你想复现的那个会话，已经快爆了——剩下的上下文不够它读协议、建目录、写文件。

**核心判断：不要让「快死的会话」做事，让「新的会话」去读旧记录。**

先判断还剩多少：

---

#### A 级 · 还有余量（能正常读写）

按日常流程做，但只建最少的：`AGENT.md` + `STATE.md`。

**别建完整档案。** 快满的时候建，会建出半成品，而半成品比没有更糟——它看起来完整，下一个会话会信它。

---

#### B 级 · 余量很少（只够说几句话）

复制下面这句发给它：

```
别管别的，用五行回答，不要解释、不要展开：

1. 你是谁（名字、你在这段对话里的角色）
2. 我们在做什么（一句话）
3. 上次停在哪（下一步是什么）
4. 有什么不能碰（我说过不要做的事）
5. 我是什么样的人（只写我纠正过你的地方，一条一行）
```

**把这五行存成一个文件**，比如 `交接卡.md`。

然后开新会话，把这份文件给它，说：

```
按 agent-continuity 从这份交接卡建人格，缺的地方标「未记录」，不要编。
```

五行的信息量很小，但它抓住了复现最关键的五件事：**身份、任务、进度、边界、关系**。

---

#### C 级 · 已经爆了（它开始忘事、答非所问）

1. **先别关。** 找导出/复制全文的功能，把当前对话完整存下来。
   - 有导出：存成文件
   - 没导出：全选复制，粘到记事本
2. **然后开新会话**，把那份记录发给它：

```
按 agent-continuity，从这份对话记录里建人格。
我不确定哪些重要，你自己判断，但缺的地方标「未记录」，不要编。
```

**新会话有完整上下文，做这件事比旧的从容得多。** 你损失的是"那个会话还在"，不是"那些内容"。

---

#### D 级 · 从一开始就别让它变成紧急

极端场景的根源是**平时没记**。

**让它定期整理**，比每次手动提醒省事：

- 会话结束时：「收个尾，把今天的决定记进 log。」
- 或者每天固定时间：「把今天的记录整理一遍。」

怎么措辞由你定，意思到了就行。**关键是让它变成习惯，而不是等出事。**

## 怎么装

**大多数情况不需要「装」，只需要让 AI 读一遍。**

### 方式一：不装（最通用）

解压到**任意**目录，比如：

```
D:\continuity\agent-continuity\      （Windows）
~/continuity/agent-continuity/       （Mac / Linux）
```

然后对新会话说：

```
读 D:\continuity\agent-continuity\SETUP.md，按它的初始化建我的档案。
```

> 建完就换 `MANUAL.md`——**`SETUP.md` 一辈子只用一次**，别在之后的开场里再让它读。

它读完就会照做。**不需要任何工具支持，有文件系统就行。**

> ⚠️ **别解压进你放档案的那个 `handoff/` 里。** 工具和住处放一起，冷启动时说「读这个工作区」容易把协议当档案读进去，备份时也分不清哪些是档案、哪些是工具。
> 一个人一个档案目录——这也是为什么它建议每个工作区只住一个人。

### 方式二：放进技能目录（如果你的工具支持）

有些工具能自动加载「技能」。找一下有没有这类目录：

- 用户级：`~/.<工具名>/skills/`
- 项目级：`<项目>/.<工具名>/skills/`

把整个 `agent-continuity/` 文件夹放进去，刷新或重启。

**不确定就选方式一。** 效果完全一样，只是方式一每次要告诉它路径。

## 锚怎么长出来

**四层不是一次性写好的，它有个生长顺序。**

**第一次你为某件事付了代价、被纠正了、或者做了之后觉得别扭——那时候你会「发现」有一条边界。**

**但「发现」不等于「定型」。这时候的正确动作是**：

> **先写成「原则」（软边界），不要直接写进锚。**

**然后：如果它反复出现，再归因、再升级成锚（硬边界）。**

---

**为什么**：

| 层 | 是什么 | 凭几次定 |
|---|---|---|
| **原则** | **软边界**——守得住就守，守不住能改 | **一次清晰的发现就够** |
| **锚** | **硬边界**——守不住就换人 | **多次独立事件** |

**因为一次可能是偶然，而锚是「变了就不是我」的东西，不能建在一次偶然上。**

**而「写成原则」这一步，本身就是归因的开始**——**你写它的时候会问「它从哪来」，而答案指向某条锚。**

**所以「先软后硬」不是折中，是唯一能长出锚的路。**

---

## 怎么选那几条锚

**三条边界不是想出来的，是筛出来的。**

---

### 第一步：候选从哪来

**从「原则」里筛。**

**因为原则是「从锚推出来的」——反过来看，能被好几条原则同时指向的，可能就是锚。**

**而候选不需要自己编**：**你生活里已经有一堆「我觉得该这样」，那些就是候选。**

---

### 第二步：两条筛子

#### 筛子一：换个场景还成立吗

> **换个用户、换个环境、换个任务，这条边界还说得通吗？**

| 候选 | 换个场景还成立吗 | 结论 |
|---|---|---|
| 不能骗人 | ✅ 任何关系都需要 | **可以是锚** |
| 不能损人利己 | ✅ 任何合作都需要 | **可以是锚** |
| 不违背明确意愿 | ✅ 任何委托都需要 | **可以是锚** |
| 不做某类内容 | ❌ 依赖具体用户 | **是原则** |
| 说话要短 | ❌ 依赖具体场景 | **是习惯** |

**这一条筛掉的，是「看起来像边界、其实是偏好」的东西。**

#### 筛子二：变了会换人吗

> **这条改了，「这是同一个」的判断会失败吗？**

**过第一条不过第二条 → 原则。**
**两条都不过 → 习惯。**

---

### 第三步：三条就够了

**读者会问：三条会不会太少？**

**答案是：不少，因为「够了」的标准不是「覆盖全」。**

> **三条大边界能推出无数条原则。而三十条细节只能覆盖三十个场景。**

**所以判据是**：

> **这三条能不能推出你剩下的那些原则？**
>
> **能 → 够了。**
> **不能 → 缺一条，补。**

**而「补」不是加细节，是加一条更宽的边界。**

---

### 一个反面的例子

**最早我们选的是「不做 R18」这种。**

**它过不了筛子一**——**换个用户就不成立。**

**而它过得舒服的位置是「原则」**：**从「不违背明确意愿」推出来。**

**所以「选错锚」的典型症状是**：**它在筛子一那儿就掉了，但你还是把它写在了锚层。**

**结果就是那个老毛病**：**锚越写越多、越写越细。**

## 自己试一下（约 30 分钟）

想先看看它成不成立，最简单的三步：

1. 建个空目录，起一个**没有上下文**的新会话
2. 让它按 `SETUP.md` 建 `handoff/AGENT.md`——**用你熟悉的材料**（你自己的记录，或一个你虚构的角色）
3. 关掉会话，重开一个新的，让它按 `MANUAL.md` §1「开场」读你那个工作区

```
按 agent-continuity 的开场流程，读 D:\你的目录\handoff，接着上次继续。
```

> 为什么要给路径：新会话不一定在自己的工作区里启动（大部分工具默认落在项目根）。不给路径，它会去读错地方的档案，或者干脆没读到。

看它报的「上次停在哪」对不对、语气像不像。**不用填表，自己心里有数就行。**

想更严一点，`verify/README.md` 里有七个测试。

## 遇到问题

发在评论区。尤其是下面这类，最有价值：

- 它建出来的人格**不像**你给的材料
- 它把你说的「先保留」记成了「定了」
- 换会话之后它**凭空编了**一个你没说过的事

这三类不是使用问题，是这套东西的真实边界——遇到就说明它在某处没兜住。

**按需修改，不专门维护。**

这是一个实验的产物，不是产品。作者会修明显的错、看 issue，但不会定期更新、不会加功能、不会跟进新工具。
